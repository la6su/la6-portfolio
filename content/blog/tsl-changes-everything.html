Why TSL Changes Everything

Three.js Shading Language (TSL) is not just a new API. It's a fundamental shift in how we write GPU code. Type safety, cross-backend compilation, and the end of raw GLSL string concatenation. Here's why we're all-in.

The old way: GLSL strings

Writing a shader used to mean writing a GLSL string inside a JavaScript file. No autocomplete. No type checking. No way to catch a typo until runtime. A shader bug that crashed the whole pipeline would show up as a black screen with a console warning buried in three.js internals. 

// The old way — raw GLSL string
const material = new THREE.ShaderMaterial({
  vertexShader: \`
    varying vec3 vNormal;
    void main() {
      vNormal = normal;
      gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
    }
  \`,
  fragmentShader: \`
    varying vec3 vNormal;
    void main() {
      gl_FragColor = vec4(vNormal * 0.5 + 0.5, 1.0);
    }
  \`,
})

This works. But it doesn't scale. Add a uniform? String concatenation. Add a chunk from another file? #include with a path that breaks if you move files. Share a function between shaders? Copy-paste.

The new way: TSL node graphs

TSL turns shaders into TypeScript. Each GPU operation is a function that returns a node. Nodes compose into graphs. The graph compiles to WGSL (WebGPU) or GLSL (WebGL2) at runtime — same code, both backends. 

// The new way — TSL node graph
import { Fn, vec3, uniform, positionLocal, normalLocal, mx_noise_float, sin, mix } from 'three/tsl'

const uTime = uniform(0)
const uDisplace = uniform(0.08)

const positionNode = Fn(() => {
  const pos = positionLocal
  const noise = mx_noise_float(pos.add(uTime))
  return pos.add(normalLocal.mul(noise.mul(uDisplace)))
})

Type safety: positionLocal is a vec3 node. mx_noise_float takes a vec3 and returns a float. The TypeScript compiler catches type mismatches before you run the code.

One graph, different backends

Three.js compiles a TSL graph for the renderer backend it initialized:

  • WGSL for the WebGPU backend
  • GLSL ES 3.0 for Three.js's WebGL2 backend

This project uses Three.js's WebGPURenderer, which selects a supported backend during initialization. The app keeps one TSL graph instead of maintaining separate WebGPU and WebGL shader implementations. Shader precision and backend support can differ, so visual output still needs to be checked on each backend.

"A shader bug that used to take 20 minutes of console.log triangulation now shows up as a type error in the editor."

What this unlocks

Iteration speed: change a node, see the result. No shader recompilation pipeline to manage — three.js handles it.

Refactoring: extract a function, reuse it across materials. The type system ensures you wire it up correctly.

Debugging: inspect the generated WGSL/GLSL if something looks wrong. But you rarely need to — the node graph is the source of truth.

One shader graph: write the effect in TSL and let Three.js compile it for the selected backend. There is no app-authored parallel GLSL path.

The catch

TSL evolves alongside three.js, so upgrades need deliberate validation across the supported render backends. The narrow type adapters in src/types/tsl-helpers.ts keep declaration gaps at one boundary instead of spreading casts through shader graphs.

The three.js examples and TSL source are useful references alongside the official documentation. Project-specific shader patterns live with the scene components and their TSL helpers.

The verdict

TSL gives this project one composable shader graph for its supported Three.js backends. That keeps visual effects in one place while Three.js handles backend selection and compilation.
